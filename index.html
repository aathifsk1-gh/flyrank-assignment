Ranking Content Pages for Refresh Review: A Transparent Baseline and Learned Score on Anonymized Search Data

Author: Aathif · Lane: Refresh / Content Opportunity Scoring
Repo: github.com/aathifsk1-gh/flyrank-assignment

Abstract

Content teams cannot review every page, so they need a ranked list of which pages are most worth refreshing first. Using an anonymized starter slice of FlyRank search data (30,000 pages), this work frames the problem as ranking: a transparent hand-written baseline score versus logistic regression and random forest models that output decline probabilities. Models are evaluated under a client-holdout split with Precision@K against the base rate and the baseline. On this sample, the learned ranker improves Precision@50 over the hand rule while remaining explainable through reason codes. The output is decision-support for editors—not a claim about Google’s ranking algorithm or causal proof that refresh recovers traffic.

1. Introduction / Problem

Decision: Which pages should an editor or SEO lead review for refresh this week?
Unit of analysis: one row = one content page.
Output: a ranked queue with priority score, suggested action, and reason codes.
Cost of a wrong call: wasted editor hours on low-value pages and delayed attention on pages that are quietly losing impressions.

A simple rule (“anything down more than 20%”) is easy to write but only moderately accurate. Volume, position, age, CTR, and depth interact in ways that are hard to capture with a few thresholds. A learned score can combine those signals; a transparent baseline keeps the system honest and comparable.

2. Data

Release: internship starter dataset data/raw/content_refresh_anonymized.csv — 30,000 pseudonymized pages × 44 columns, 32 clients. Metrics are trailing 90-day aggregates; trend compares the last 30 days vs the previous 30 days.

What was excluded (and why):

  • Client names, domains, URLs, titles, raw queries — not present in the export; never added.
  • trend_direction / trend_pct as features — they define the label (leakage).
  • content_id / client_id as model inputs — used only for grouping and client-holdout splits.
  • Generation metadata (provider_used, model_used) — not performance signals for ranking.
About 54% of pages are labeled declining (trend_direction == "down"). Declining pages still show solid median impressions (~961), so the problem is not only low-traffic noise. Roughly 73% of pages clear a basic volume filter (impressions ≥ 100 and sessions > 0).

3. Methodology

Label is_declining_label = (trend_direction == "down") — observed impression trend, not a product rule.

Features Impressions, clicks, sessions, CTR, average position, engagement/scroll rates, word count, content age, days since update, keyword context where available, content type and position tier (one-hot). No trend fields, no IDs.

Baseline Transparent score: 0.40·visibility + 0.30·freshness risk + 0.25·position opportunity + 0.05·depth gap, with reason codes such as stale_visible_page, declining_with_demand, thin_visible_page, low_ctr_visible_page.

Models Logistic regression (readable) and random forest (non-linear interactions). Ranking uses predicted probability of decline.

Validation Client-holdout (~20% of clients). Primary metric: Precision@50 (also @20 and @100), always next to the test base rate.

Leakage checks Trend columns excluded from features. A deliberate test that adds trend_pct inflates Precision@50 — confirming the harness detects label leakage. Product decision flags are not in the export and were not rebuilt as features.

5. Limitations & honest framing

  • Single snapshot; label and features share the same 90-day view (no true forward window).
  • Client-holdout on 32 clients is stricter than random rows but still small vs the full warehouse.
  • Keyword fields are missing systematically by content type; naive fill can encode type.
  • No causal claim that refreshing causes recovery.
  • Not a reverse-engineering of Google’s ranking systems—only prioritisation support on observed decline in this sample.
Language used throughout: observed, measured, directional, decision-support.

6. Ranked recommendations (action playbook)

Editors should treat the queue as a starting list, not an automatic publish pipeline.

  • refresh — stale or declining-with-demand pages with meaningful volume
  • expand_and_refresh — thin but visible pages
  • refresh_and_review_ctr — decent position/volume but weak CTR
  • monitor — low model probability / soft signals

Human checks before acting: strategic importance, seasonality, in-flight work, live page vs reason codes.

No-go automation: bulk overwrite/delete, unreviewed mass meta changes, any use of this data to re-identify clients.
